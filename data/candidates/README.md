# 候选池 v1

## 为什么需要它

如果让模型自由生成推荐内容，`published_at` 也会是它现编的。那样评测的「时效性」维度
测到的其实是**模型编日期的水平**，不是内容的新鲜度——整个维度失效。

候选池让模型只能**从给定条目里挑选**，日期因此是确定的、可复核的。

## 字段

| 列 | 说明 |
|---|---|
| `id` | 候选编号 C001–C080 |
| `title` | 标题 |
| `category` | 受控词表八类之一 |
| `summary` | 一句话摘要（给模型做选择依据） |
| `age_days` | **距评测日的天数**，不是绝对日期 |

## 为什么存 age_days 而不是 published_at

绝对日期会让数据随真实时间"变旧"：10 月造的池子，12 月跑评测时所有条目都超过 60 天，
时效性维度全部 0 分，评测就没意义了。

存相对天数后，加载时按当前评测日现算：

```
published_at = 评测日 - age_days
```

这样无论哪天跑，三个档位的分布都是稳定的，结果可复现。

## 分布

| 维度 | 分布 |
|---|---|
| 类目 | 8 类 × 10 条 |
| 年龄 | ≤30 天 29 条 / 31–60 天 23 条 / >60 天 28 条 |

同时覆盖三个档位，任何一组 5 条都能出现不同分数。
