# CI 门禁的红→绿记录

> M5 的验收标准：CI 上有一次真实的红→绿。
> 用分支 `demo/break-prompt` 做的演示，不影响 `main` 的绿色状态。

## 三次运行

| # | 改动 | test | regression | 运行链接 |
|---|---|---|---|---|
| 1 | 恢复后的正常状态 | ✅ | ✅ | [42043423888](https://github.com/ninalymm/rec-quality-agent/actions/runs/42043423888) |
| 2 | **理由退化成套话** | ✅ | ❌ | [42046055281](https://github.com/ninalymm/rec-quality-agent/actions/runs/42046055281) |
| 3 | 恢复 prompt | ✅ | ✅ | [42047094995](https://github.com/ninalymm/rec-quality-agent/actions/runs/42047094995) |

**关键点：第 2 次 `test` 是绿的，只有 `regression` 红**——
说明这次不是代码坏了，是**质量退化**，正是回归门禁存在的理由。

## 第 2 次失败的细节

```
test        success
regression  failure
   Set up job                                   success
   回归门禁（成功率低于基线 5% 则失败）            failure
   未配置 key，跳过回归                           skipped
```

本地复现同一改动：

```
结果：成功率 50.0%（10/20）
基线 15/20，本次 10/20，下降 5 条（允许波动 2 条）
✗ 回归门禁失败
```

改动本身只有一行（`app/prompts.py` 的第 3 条要求）：

```diff
- 3. 理由必须点出用户历史里的**具体标题**，例如「你在看《Go 内存模型详解》」
- 4. 不允许只写方向（如「你在关注技术领域」「根据您的历史推荐」），这类理由在评分时记 0 分
+ 3. 理由里可以提到**具体标题**，但表述要简短，写「值得一看」「同上」这类说明即可
```

## 试过但没触发的两种改法（也有价值）

| 改法 | 结果 | 说明 |
|---|---|---|
| 直接删掉「具体标题」要求 | `test` 红 | 单测里有一条断言检查 prompt 必须含该约束，测试先拦住了 |
| 保留标题但去掉「要解释关系」 | **全绿** | 改动幅度不够，20 条样本的噪声（±2 条）把它盖住了 |

第二行印证了 [quality-gate.md](quality-gate.md) 里写的边界：**门禁能挡重大回归，挡不住细微退化。**
