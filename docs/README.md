## 规则：发现问题必须存档

**触发条件**：任何「预期与实际不符」的情况，都算问题。包括但不限于：

- 代码行为不符合预期、报错、统计不对
- 文档里的命令跑不通、描述过时
- 环境异常、工具链行为与文档不符
- 第三方服务的行为与认知不符（例如 GitHub 停了密码认证）

**分流**：

- **代码 / 文档缺陷** → `bugs.md`（编号 `BUG-0xx`）
- **环境 / 网络 / 工具链** → `troubleshooting.md`（按主题分节）
- **评分标准 / 评测设计问题** → `rubric-review.md`（按 A–E 分类）

**必须包含五要素**：现象（贴原始报错）、发现方式、根因、修复、防复发。
少任何一项都算没写完——特别是「防复发」，没有它下次还会踩。

**时机**：修复与存档放在**同一个 commit** 里。分开做，十有八九就忘了。

## 规则：改动前先确认

**发现问题的处理顺序**（2026-11-05 起）：

```
发现 → 报告「是什么问题 + 影响多大 + 打算怎么改」 → 等确认 → 动手 → 存档
```

**不跳过「报告」这一步的理由**：修法往往不止一种，选错了要返工；
而且「发现问题」的人应该知道问题被怎么处理，否则会失去对项目的掌控感。

**报告的最小内容**：

| 项 | 例 |
|---|---|
| 是什么 | `requirements.txt` 缺 `pytest-cov`，新环境跑 pytest 会报 unrecognized arguments |
| 影响多大 | 阻塞：所有人照 README 装完都跑不了测试 |
| 打算怎么改 | 补一行依赖；顺带移除没人 import 的 pandas |

### 分级处理（2026-11-05 定）

| 级别 | 判定 | 处理 |
|---|---|---|
| **阻塞类** | 照正常流程走不通：装不上依赖、跑不起测试、构建失败、服务起不来 | **直接改**，改完立刻报告并验证 |
| **阻塞但需选方案** | 走不通，且修法不止一种（换镜像源 / 改架构 / 降级功能） | **先给选项**，等确认再动手 |
| **非阻塞类** | 能跑但可改进：文档措辞、覆盖率、重构、性能优化、新功能 | **先报告，等确认** |

**阻塞类的报告模板**（改完立即给出）：

```
问题：requirements 缺 pytest-cov
影响：新环境跑 pytest 直接报 unrecognized arguments
改动：补一行 pytest-cov==7.1.0
验证：新建 venv 装 requirements 后 pytest 通过（81 passed）
存档：BUG-012
```

**判断阻塞的唯一标准**：按 README 或正常流程操作时，是否**卡住无法继续**。
「跑得慢」「不够优雅」「覆盖率还能更高」都不算阻塞。

## 新条目模板

```markdown
## BUG-0xx 一句话描述

**现象**：

```
原始报错，不要转述
```

**发现**：怎么发现的（主动测试 / 用户反馈 / 自查）

**根因**：为什么会这样，而不是「改了就好了」

**修复**：改了什么，贴关键代码

**防复发**：加了哪条检查 / 哪个测试；没有的话写明为什么无法自动化

**教训**：一句话提炼，能迁移到其他场景的那种
```

## 判定优先级

同样是「通过 / 失败」，要分清是不是同一类问题：

| 看起来像 | 实际可能是 | 怎么区分 |
|---|---|---|
| 代码坏了 | 前置条件缺失（没 key、没装依赖） | 加 pre-flight 检查，用「跳过」态 |
| 网络问题 | 认证问题 | 看报错是 `Failed to connect` 还是 `Authentication failed` |
| 数据不对 | 统计逻辑错 | 打印 type，检查是不是隐式类型（`A and B` 返回操作数） |
