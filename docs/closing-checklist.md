# 里程碑收尾清单

> 每个里程碑（M0–M6）结束时逐条核对，**不允许「感觉做完了」就算完**。
> 用途：防止「代码写完但没推」「文档没更新」「临时文件留在仓库里」这类事后再也说不清的问题。

## 通用收尾项（每个里程碑都要过）

| # | 检查项 | 怎么确认 | 常见遗漏 |
|---|---|---|---|
| 1 | **代码已提交并推送** | `git status` 干净、`git log origin/main..HEAD` 为空 | 改了但忘了 commit；commit 了但忘了 push |
| 2 | **测试与覆盖率达标** | `pytest -q` 全绿，覆盖率 ≥ 60% | 只跑了部分用例；新代码没进测试 |
| 3 | **验收标准逐条核过** | 对里程碑表里的「验收标准」逐项打勾，每项给出证据 | 用「差不多」代替证据 |
| 4 | **文档同步到最新** | README 的状态/数字、PROGRESS、milestones 三处一致 | 改了代码没改 README 里的数字 |
| 5 | **新发现的坑已存档** | `docs/bugs.md` / `troubleshooting.md` 有对应编号 | 修完就忘，下次再踩 |
| 6 | **遗留问题写明状态** | 未解决项标注「为什么没做 / 何时做」 | 假装不存在 |
| 7 | **临时产物已清理** | 验证目录、临时脚本、`.coverage`、生成文件（**清理前先分类，见下节**） | 把一次性验证当成产物留在仓库 |
| 8 | **下一阶段的入口确认** | 下一步做什么、依赖是否就绪 | 收尾完不知道下一步 |

## 清理前的分类规则（第 7 项的展开）

「清理临时文件」最容易出事，因为命令行不区分东西是谁的。**删之前必须把每个条目归到三类之一**：

| 类别 | 判断依据 | 处理 |
|---|---|---|
| **A. 我创建的** | 知道它是什么、什么时候生成的（验证克隆、临时脚本、导出文件） | 直接删 |
| **B. 系统 / 运行中的应用在用** | 属主是 `root`，或者有进程正在使用（socket、pid、锁文件、缓存目录） | **不删**，删了会弄坏环境 |
| **C. 用户自己的** | 名字像笔记、数据、文档，但不是本次生成的 | **先问**，不要按「都可以删」处理 |

**目录本身**：系统目录（`/tmp`、`/var/tmp`、`~/Library/Caches`）只清内容，不删目录。
它们是系统路径的一部分（`/tmp` 还是 `/private/tmp` 的软链），删掉会破坏其他程序。

### 一个真实案例（2026-11-05）

清 `/private/tmp` 时，25 个条目分成：

- **A 类 10 个**：临时脚本、抓包 html、空锁文件 → 删除
- **B 类 11 个**：`boost_interprocess`（26M，root）、Docker 特权目录、
  搜狗输入法目录、root 的 socket/管道 → 保留
- **C 类 4 个**：`daily-1104.txt`、`daily-1105.txt`、`外企-1103.json`、`外企-1104.json`
  → 名字像用户笔记与求职数据，**问过之后确认是用户的，保留**

如果按字面执行「这个文件夹里都可以删」，C 类会被误删，B 类会弄坏 Docker 和输入法。

## 各里程碑的专属验收项

| 里程碑 | 专属验收 |
|---|---|
| M0 | 能跑通一次真实 LLM 调用；验收脚本全绿 |
| M1 | 陌生人能照 rubric 打分；200 条 query 与检查点齐全 |
| M2 | 报告里有 kappa / 位置偏差 / 成本三个数字，且能解释怎么算的 |
| M3 | `curl` 能拿到结果；trace 能看到每步输入输出与耗时 |
| M4 | 新环境照 README 10 分钟跑通（**必须由非开发环境验证**） |
| M5 | CI 上有一次真实的红→绿记录（截图存证） |
| M6 | 对着人讲完不卡壳；demo 视频与讲稿可独立阅读 |

## 一个真实的收尾案例（M4，2026-11-05）

收尾时按本清单核对，发现三处遗漏：

| 检查项 | 当时状态 | 处理 |
|---|---|---|
| 7 临时产物 | `/tmp/recqa-fresh`（53MB 验证克隆）未删；`.coverage` 与 `data/evaluated_*.jsonl` 被误提交 | 删除验证目录；产物问题待处理 |
| 6 遗留问题 | Docker 路径没做第二方复现 | 写进 PROGRESS「没完成」栏 |
| 4 文档同步 | PROGRESS 里写「74 个测试」，实际 83 | 已改 |

**教训**：收尾不是「功能做完了」，而是「这件事可以交给别人了」。
功能完成度和可交付度是两件事——前者自己知道，后者要靠清单确认。
