# 推荐质量评分标准 v0.2

> 状态：维度1 已定稿；维度2 采用 B 方案（兴趣主题）；维度3 按「类型数」定义。
> 仍待定：聚合规则、是否补语义维度（见文末）。

## 0. 通用规则

| 项 | 规则 |
|---|---|
| 评分对象 | 5 条推荐内容（每条含 `category`、`published_at`） |
| 粒度 | 0 / 1 / 2 三档（档位越少，标注方差越小） |
| 输出 | 每维 `score` + 一句话 `evidence`，evidence 要能被第三人复核 |
| 数据缺失 | 记 `null`，不计入均值，单独统计缺失率（不把数据质量问题扣成推荐质量问题） |
| 执行正确性 | 工具报错、参数对错**不属于本表**，另设维度，M3 起启用 |

### 类目词表（受控）

维度2 和维度3 都依赖 `category` 字段，必须受控，否则「技术深度 / 技术 / 科技」会被算成三个类型：

```
技术 / 职场 / 理财 / 健康运动 / 生活方式 / 教育 / 娱乐 / 其他
```

规则：推荐结果里的 `category` 必须取自该词表；不在词表内的，一律归入「其他」。生成时校验，不依赖 judge 判断。

## 维度1 内容有效性（时效性）

**定义**：推荐内容的发布日期距评测日的天数。
**执行方式**：**由代码计算，不交给 judge**（确定性计算，交给 LLM 只会引入方差）。

| 分 | 条件 | 示例（评测日 2026-10-29） |
|---|---|---|
| 2 | 0 ≤ 天数 ≤ 30 | 2026-09-29 ~ 2026-10-29 |
| 1 | 30 < 天数 ≤ 60 | 2026-08-30 ~ 2026-09-28 |
| 0 | 天数 > 60 | 2026-08-29 及更早 |
| null | 无法判定 | 缺日期 / 未来日期 / 格式异常 |

```
天数 = (评测日 - published_at).days     # 自然日，评测日固定为批次执行日
```

## 维度2 兴趣相关性

**定义**：5 条推荐中，类型命中用户「已表达兴趣主题」的条数。
**判定依据**：`interest_categories` —— 用户行为历史（收藏 / 点赞 / 浏览）中出现过的类目去重集合，按上面的受控词表归类。

| 分 | 条件 |
|---|---|
| 2 | 命中 ≥ 4 条 |
| 1 | 命中 2–3 条 |
| 0 | 命中 ≤ 1 条 |
| null | `interest_categories` 缺失（用户无历史行为） |

**判定式**（代码可算，不需要 judge）：

```
hits = [r for r in recs if r.category in user.interest_categories]
```

**为什么从「具体内容」改成「兴趣主题」**：

- 原定义要求「推荐的就是他收藏过的那条」，等于奖励复现历史，与维度1（越新越好）方向冲突
- 上升到类目后，推荐新内容也能命中兴趣，两个维度不再互相打架

**已知局限**：浏览行为是弱信号（误点也算），会稀释 `interest_categories`。当前不做权重（加权会引入主观判断、降低一致性），记录在案，M2 观察影响。

## 维度3 内容多样性

**定义**：5 条推荐覆盖的**类型数**（`category` 去重计数，按受控词表）。

| 分 | 条件 |
|---|---|
| 2 | 类型数 ≥ 3 |
| 1 | 类型数 = 2 |
| 0 | 类型数 ≤ 1 |

```
types = len({r.category for r in recs})
```

**为什么用「类型」而不是「关键词数」**：关键词由谁产出不可控，且数量不等于主题数（5 条全讲 Go，关键词仍有 Go / 内存 / GC 三个）。用受控词表里的 `category` 计数，口径唯一、可复算。

## 维度间的关系：留一个「探索位」

维度2 和维度3 存在结构性张力：

- 维度2 奖励「都在用户兴趣内」
- 维度3 奖励「类型要分散」

如果用户只表达过 2 个兴趣类目（比如「技术」「健康运动」），那么**要拿维度3 的 2 分（≥3 类型），必然有 1 条落到兴趣之外**，维度2 就要扣分。

两个门槛是这样对齐的：

| 场景 | 5 条构成 | 维度2 | 维度3 |
|---|---|---|---|
| 全在兴趣内 | 技术 3 + 运动 2 | 2 分（5 条命中） | 1 分（2 类型） |
| **留一个探索位** | 技术 3 + 运动 1 + 职场 1 | **2 分（4 条命中）** | **2 分（3 类型）** |
| 探索过多 | 技术 2 + 运动 1 + 职场 1 + 娱乐 1 | 1 分（3 条命中） | 2 分 |

所以**最优解是「4 条命中 + 1 条探索 + 覆盖 3 个类型」**，两个维度同时 2 分。这个结构是刻意设计的：它奖励「有一点点探索」，惩罚「全是同质内容」和「跑题太远」。

建议在 `queries.csv` 的 `request` 里明确写「给我推荐 5 条，可以有一两条新方向」，让这个设计意图在数据里可见。

## 执行方式：哪些交给代码，哪些交给 judge

| 维度 | 执行方 | 原因 |
|---|---|---|
| 维度1 时效性 | 代码 | 日期差是确定性计算 |
| 维度2 兴趣相关性 | 代码 | 集合命中判断 |
| 维度3 内容多样性 | 代码 | 去重计数 |

**注意**：按当前定义，三个维度全部可由代码算出，**没有需要 judge 做语义判断的维度**。

这会直接影响 M2：双 judge 的一致性（kappa）会始终接近 1.0（因为判分是确定性的），拿不到「模型裁判可信吗」这个结论。

两个选择：

- **A（推荐）**：保留这 3 个确定性维度作为「客观层」，另加 1 个语义维度（如**理由可解释性**：推荐理由是否引用了用户历史中的具体条目）。语义维度才需要 judge，kappa 才有意义
- **B**：只用 3 个确定性维度，M2 的重心改成「类目抽取一致性」（即模型给推荐打 category 的准确率）

选 A 的话，M2 的叙事更完整：客观维度全对（1.0）+ 语义维度有真实分歧（0.5–0.7），能讲清「哪些该交给机器、哪些必须人来定」。

## 数据字段要求

`data/queries.csv` 需要新增一列：

| 列 | 说明 |
|---|---|
| `qid` | 题号 |
| `user_profile` | 用户画像 |
| `history` | 行为历史（文本，给人看） |
| `interest_categories` | **新增**：行为历史涉及的类目，分号分隔，如 `技术;健康运动` |
| `request` | 用户请求 |

推荐输出需要字段：`title`、`category`（受控词表）、`reason`、`published_at`（YYYY-MM-DD）。
