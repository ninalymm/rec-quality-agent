# 推荐质量评分标准 v0.1

> 状态：**维度1 已定稿**；维度2、3 待确认；评分对象（推荐内容 / Agent 工具轨迹）待确认。
> 进度记录见文末「待定事项」。

## 通用规则

- **粒度**：0 / 1 / 2 三档（档位越少，标注方差越小，kappa 越高）
- **输出**：每个维度给 `score` + 一句话 `evidence`，evidence 要能被第三人复核
- **数据缺失**：记 `null`，不计入均值，单独统计缺失率（不把「没数据」扣成 0 分）
- **不在本表内的**：工具报错、参数对错属于「执行正确性」，另设维度，M3 起启用

## 维度1 内容有效性（时效性）

**定义**：推荐内容的发布日期距**评测日**的天数。
**执行方式**：**由代码计算，不交给 judge**——日期差是确定性计算，交给 LLM 只会引入方差。

### 判定表（区间互斥，无空档）

| 分 | 条件 | 示例（评测日 2026-10-29） |
|---|---|---|
| 2 | 0 ≤ 天数 ≤ 30 | 2026-09-29 ~ 2026-10-29 → 2 分 |
| 1 | 30 < 天数 ≤ 60 | 2026-08-30 ~ 2026-09-28 → 1 分 |
| 0 | 天数 > 60 | 2026-08-29 及更早 → 0 分 |
| null | 无法判定（见边界规则） | — |

> 原稿的三档是嵌套的（近30 ⊂ 近60 ⊂ 近90），且 91 天以后没有归属。
> 现改为互斥区间，并把「90 天」这条冗余边界去掉：60 天以上一律 0 分。

### 计算口径

```
天数 = (评测日 - published_at).days      # 自然日，按 YYYY-MM-DD 计算
评测日 = 评测执行当天（Asia/Shanghai）    # 同一批次固定，不随运行时刻漂移
```

### 边界规则

| 情况 | 处理 | 理由 |
|---|---|---|
| 缺 `published_at` | `null` | 数据质量问题，不该扣推荐分 |
| 日期在未来 | `null` | 数据异常，不是推荐质量问题 |
| 日期格式无法解析 | `null` | 同上 |
| 同日发布（天数 = 0） | 2 分 | 落在 0 ≤ 天数 ≤ 30 内 |
| 评测日当天 23:59 运行 | 仍按当日算，不跨天 | 批次内一致性 |

### 输出示例

```json
{"content_validity": {"score": 2, "evidence": "发布于 2026-10-20，距评测日 9 天，落在 ≤30 天档"}}
```

## 维度3 待定：内容多样性

原稿判定依据是「推荐内容包含的关键词数量」，存在三个待解决问题：

1. 关键词由谁产出（judge 抽取 / 结果字段）未定义，不同来源数量不可比
2. 关键词数不等于主题数：5 条全讲 Go，关键词可以是 Go / 内存 / GC，仍是单一主题
3. 原稿写「不足 1 个」，应为「0 个」

待确认后再定稿。
