# 推荐质量评分标准 v1.0

> 状态：**四个维度全部定稿，聚合规则已定。**
> 评分对象：一次生成的 5 条推荐（含理由）。

## 0. 通用规则

| 项 | 规则 |
|---|---|
| 评分对象 | 5 条推荐内容（每条含 `title`、`category`、`reason`、`published_at`） |
| 粒度 | 0 / 1 / 2 三档（档位越少，标注方差越小） |
| 输出 | 每维 `score` + 一句话 `evidence`，evidence 要能被第三人复核 |
| 数据缺失 | 记 `null`，不参与通过判定，单独统计缺失率（不把数据质量问题扣成推荐质量问题） |
| 执行正确性 | 工具报错、参数对错**不属于本表**，另设维度，M3 起启用 |

### 类目词表（受控）

维度2、维度3 都依赖 `category`，必须受控，否则「技术深度 / 技术 / 科技」会被算成三个类型：

```
技术 / 职场 / 理财 / 健康运动 / 生活方式 / 教育 / 娱乐 / 其他
```

不在词表内的一律归「其他」。生成时校验，不依赖 judge 判断。

### 维度总览

| # | 维度 | 类型 | 执行方 |
|---|---|---|---|
| 1 | 内容有效性（时效性） | 客观 | 代码 |
| 2 | 兴趣相关性 | 客观 | 代码 |
| 3 | 内容多样性 | 客观 | 代码 |
| 4 | 理由可解释性 | **语义** | **judge（LLM）** |

## 打分顺序（必须按此顺序，否则会互相污染）

维度2 和维度3 都基于 `category`，先数哪个会导致不同结果。**固定按下面四步走**：

```
第 1 步  数类型 → 维度3
         把 5 条的 category 写下来，去重，数有几个不同的值
         注意：包含所有类型，不排除「不在兴趣内」的

第 2 步  数命中 → 维度2
         把 5 条的 category 逐个与 interest_categories 比对，数有几条命中
         分母永远是 5，不剔除任何条目

第 3 步  算日期 → 维度1
         逐条算 (评测日 - published_at).days，按最旧的那条定档？不，按 5 条分别定档后取平均？见下

第 4 步  读理由 → 维度4（唯一需要语义判断的一步，放最后，避免影响前三步）
```

**前三步是机械操作，不要在这一步做「这条内容好不好」的判断。** 内容质量由维度4 承担。

### 第 3 步的细节

维度1 是对整组打一个分，按 5 条天数的**中位数**所在档位取值（2026-10-31 确认）：

- 5 条天数的中位数落在 ≤30 → 2 分
- 落在 31–60 → 1 分
- 落在 >60 → 0 分
- 任一条无法判定 → 该条跳过；若可判定条目 < 3，整组记 null

> 用中位数而不是最小值：推荐是给用户的一整屏，个别旧内容不该把整组拉到 0 分；取平均又容易被一组极值带偏。中位数对应「整屏的典型新鲜度」。

## 维度1 内容有效性（时效性）

**定义**：推荐内容的发布日期距评测日的天数。
**执行方**：代码（日期差是确定性计算，交给 LLM 只会引入方差）。

| 分 | 条件 | 示例（评测日 2026-10-29） |
|---|---|---|
| 2 | 0 ≤ 天数 ≤ 30 | 2026-09-29 ~ 2026-10-29 |
| 1 | 30 < 天数 ≤ 60 | 2026-08-30 ~ 2026-09-28 |
| 0 | 天数 > 60 | 2026-08-29 及更早 |
| null | 无法判定 | 缺日期 / 未来日期 / 格式异常 |

```
天数 = (评测日 - published_at).days      # 自然日；评测日固定为批次执行日
```

---

## 维度2 兴趣相关性

**定义**：5 条推荐中，类型命中用户「已表达兴趣主题」的条数。
**判定依据**：`interest_categories` —— 行为历史（收藏 / 点赞 / 浏览）中出现过的类目去重集合。
**执行方**：代码。

| 分 | 条件 |
|---|---|
| 2 | 命中 ≥ 4 条 |
| 1 | 命中 2–3 条 |
| 0 | 命中 ≤ 1 条 |
| null | `interest_categories` 缺失（用户无历史） |

```
hits = [r for r in recs if r.category in user.interest_categories]
```

**分母恒为 5，不剔除任何条目。** 内容质量差不影响本条——那是维度4 的事。

**已知局限**：浏览是弱信号（误点也算），会稀释 `interest_categories`。当前不做加权（加权引入主观判断、降低一致性），记录在案，M2 观察影响。

---

## 维度3 内容多样性

**定义**：5 条推荐覆盖的类型数（`category` 去重计数）。
**执行方**：代码。

| 分 | 条件 |
|---|---|
| 2 | 类型数 ≥ 3 |
| 1 | 类型数 = 2 |
| 0 | 类型数 ≤ 1 |

```
types = len({r.category for r in recs})
```

**统计全部 5 条的类目，不排除「不在兴趣内」的类型。** 例如兴趣只有「技术、健康运动」，5 条里出现 1 条「职场」，类型数仍算 3。

用受控词表的 `category` 计数，而不是「关键词数」——关键词来源不可控，且数量不等于主题数（5 条全讲 Go，关键词仍有 Go / 内存 / GC）。

---

## 维度4 理由可解释性

**定义**：5 条推荐的理由中，有多少条**引用用户历史行为里的具体信息**（而不是泛泛而谈）。
**执行方**：**judge（LLM）**——这是唯一需要语义判断的维度。

### 判定标准

| 等级 | 定义 | 例 |
|---|---|---|
| **引用具体（记 1 条）** | 理由指向历史中的**具体条目或事件**，可核对 | 「你最近看了《Go 内存模型详解》，这篇讲 Go 调度器，属于同源问题」 |
| **仅到类目（不算具体）** | 理由只提到类目/方向，任何同类用户都能套用 | 「你在技术类内容上有浏览记录，这篇属于技术方向」 |
| **空泛（不算具体）** | 无指向或套话 | 「根据您的历史行为为您推荐」「猜你喜欢」 |

| 分 | 条件 |
|---|---|
| 2 | 引用具体的条数 ≥ 4 |
| 1 | 引用具体的条数 2–3 |
| 0 | 引用具体的条数 ≤ 1 |

### 反例（防止判宽）

> 「因为你关注技术领域，所以推荐这篇」——提到了方向，但没有指向任何一条历史记录，任何技术用户都能收到这句话 → **不算具体**。
>
> 「你上周看过《跑步膝伤怎么恢复》，这篇讲跑鞋选购，同属运动防护」——指向了具体条目，可核对 → **算具体**。

### 为什么这条不能交给代码

「是否引用了历史中的具体信息」需要对语义做判断：同一个理由，可能换个说法仍然引用了，也可能字面出现了关键词但逻辑不成立。这类判断只能靠模型或人，也正是 M2 要测「judge 靠不靠谱」的地方。

## 维度间的关系：留一个「探索位」

维度2 与维度3 方向相反：一个奖励「都在兴趣内」，一个奖励「类型要分散」。若用户只有 2 个兴趣类目，拿维度3 的 2 分必然有 1 条出圈，维度2 扣分。

门槛这样对齐，保证最优解存在：

| 5 条构成 | 维度2 | 维度3 |
|---|---|---|
| 技术 3 + 运动 2（全在兴趣内） | 2（5 命中） | **1**（2 类型） |
| 技术 3 + 运动 1 + 职场 1 | **2（4 命中）** | **2（3 类型）** |
| 技术 2 + 运动 1 + 职场 1 + 娱乐 1 | 1（3 命中） | 2（4 类型） |

**最优解 = 4 条命中 + 1 条探索 + 覆盖 3 个类型**，两维同时满分。这是刻意留的「探索位」：奖励一点点探索，惩罚同质化和过度跑题。

建议 `request` 里写明「可以有一两条新方向」，让设计意图在数据里可见。

## 聚合规则

### 通过判定

**四个维度均 ≥ 1 视为通过。**

```
passed = all(score >= 1 for score in dims if score is not None)
```

- 任一维度为 0 → 不通过
- 某维度为 `null` → 该维度不参与判定，样本标记为 `partial`，单独统计缺失率

### 总分

**总分 = 四个维度之和，范围 0–8，越高越好。**

```
total = timeliness + relevance + diversity + explainability    # 0–8
```

- 任一维度为 `null` → 总分记 `null`，不参与均值计算（避免用数据缺失惩罚推荐质量）
- 总分用于排序和回归基线；通过率用于 M5 门禁

### 评级（便于报告展示）

| 总分 | 评级 |
|---|---|
| 7–8 | 优秀 |
| 5–6 | 合格 |
| 3–4 | 待改进 |
| 0–2 | 不合格 |
